# Diagnostic interpretation

Read the complete result object before editing:

- `exitClassification` describes the requested command outcome.
- `requestedDimensions` identifies what the command attempted to establish.
- each status keeps its own state and diagnostic IDs;
- diagnostics include stable IDs, severity, dimension, source locations or objects when known, and a suggested next command;
- artifact paths identify durable evidence;
- project metadata binds the result to project, source, configuration, lock, and tscircuit identities.

Use the diagnostic ID, not just message text, to track a finding across reruns. Confirm that a cited report belongs to the current source digest.

Classify before repairing:

- **Source defect:** a bounded source edit can correct it.
- **Unsupported:** Fulmetry cannot honestly represent or verify the construct.
- **Incomplete:** required evidence has not been produced.
- **Unavailable:** a required qualified capability or tool cannot run.
- **External failure:** a selected external tool failed, timed out, changed, or produced invalid evidence.

Only the source-defect class normally leads directly to a circuit patch.

## tscircuit warning triage

Do not call every emitted warning an electrical violation. Fulmetry intentionally
does not make these authoring or placement hints block electrical assurance:

- unnamed traces generated by component `connections` props;
- reference-designator style recommendations when an exact device has no
  matching tscircuit primitive;
- connector accessibility direction derived from a CAD model whose insertion
  vector can disagree with an independently authored footprint rotation.

The connector hint still deserves a physical inspection: compare the actual
mouth/cable datum, footprint rotation, board edge, enclosure opening, and 3D
model transform. A false CAD insertion vector is not proof that the connector
is accessible.

Pin underspecification and missing power/ground warnings are different. Add
truthful `pinAttributes`, then follow any resulting
`ELECTRICAL_PIN_OBLIGATION_001` finding through the source/provider chain. For
unpowered passive or protection chips, use an accurate semantic primitive or
an explicit qualified device description; never fabricate power or ground
requirements to make the report green.

## Routing congestion decision tree

For an incomplete route, high clearance count, or router timeout:

1. Confirm that the candidate used the intended units, layer stack, obstacles, and distinct rule classes. Treat a single global rule as potentially over-broad around fine-pitch pads.
2. Keep `0.20 mm` as the ordinary general-clearance target. Permit a local `0.15 mm` fine-pitch breakout only when the selected fabrication profile qualifies that exact geometry; reserve `0.10 mm` for explicitly supported exceptional cases. Never lower the global rule just to make an autorouter finish.
3. Inspect conflict locations and remaining airwires. Repair orientation, escape direction, component spacing, and routing channels before changing the outline.
4. If congestion remains and the board dimensions are not mechanically fixed, enlarge the constrained axis or region by a small documented increment, preserve connector and mounting datums, then place and route again. If dimensions are fixed, report the mechanical conflict and request a requirement decision instead of resizing silently.
5. Compare before/after unrouted-net and DRC counts and rerun all affected checks. A reduction is progress, not passage; completion still requires routed connectivity and zero unwaived applicable violations.

Do not confuse component footprint selection with board-outline enlargement. Never alter a verified land pattern to gain routing space.
